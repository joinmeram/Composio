What the agent got wrong — and what fixing it took

Three real bugs were caught by manually diffing a small batch before trusting the pipeline at scale. All three are fixed and confirmed holding at n=10 — every row in this run is labeled correctly.

Bug 1 · Row mislabeling — fixed, confirmed at scale

The original write-back expression, {{ $('Loop Over Items').first(1, $runIndex).json.id }}, doesn't track loop position — five of the first five rows shipped correctly-researched content under the wrong company name.

Fix applied: an Edit Fields node now snapshots id/app/category/hint_url immediately after the row is read, before the AI Agent ever touches them. A Merge (combine by position) node reattaches those trusted values to the AI's research output afterward. All 10 rows in the latest run — Salesforce through DealCloud — are labeled correctly.

Bug 2 · Verification accuracy silently reporting 0% — fixed

The comparison code looked for columns named verification_access_model etc., but the actual sheet headers were typo'd as verifcation_access_model (and one header had a stray "ion" fragment from a copy-paste slip). Every lookup silently returned undefined, so the pipeline's own accuracy metric — the thing the assignment weighs most — was structurally incapable of reporting anything but mismatches.

Fix applied: sheet headers corrected to consistent verification_* naming, and the comparison logic now deliberately excludes free-text fields (description, blocker, credential acquisition) from the match/mismatch count. It also normalizes tokens ("OAuth 2.0" and "OAuth2" now count as equal) so formatting drift doesn't register as a false mismatch. The verification section below shows this running correctly on 2 real apps.

Bug 3 · auth_methods fragmenting into fake entries — fixed

The agent was returning full descriptive sentences inside the auth_methods array, which then split into several fake "methods" during pattern analysis.

Fix applied: the prompt now constrains auth_methods to a short controlled vocabulary (OAuth2 / API Key / Basic Auth / Token / Other), with a separate auth_notes field holding the nuance. All 10 rows in this run use clean tokens.

How the research runs

Three separate n8n workflows, chained by a shared Google Sheet acting as the data store between stages.

RESEARCH

Per-app discovery agent

Reads the 100-app list from Sheets, loops one app at a time through a Claude agent with a Tavily search tool attached. The agent is instructed to prioritize official developer docs, treat API existence as separate from self-serve access, return auth methods as controlled tokens (not free sentences), and cite evidence URLs for every claim. An Edit Fields + Merge (combine-by-position) step keeps the row's true id/app/category/hint_url out of the model's hands entirely, so the write-back can never mislabel a row no matter what the model returns.

n8n Claude Haiku 4.5 Tavily search Google Sheets
VERIFY

Independent re-research agent

A second agent researches the same app from scratch — no access to the first pass's output — with an explicit instruction set: OAuth existing doesn't prove credentials are freely obtainable, an ordinary API isn't an MCP server, say "unknown" rather than guess. Its output lands in a separate sheet tab.

n8n Claude Haiku 4.5 Tavily search
ANALYZE

Comparison & pattern code

Code nodes join the research and verification tabs on app id, diff them field by field on the controlled-vocabulary fields only (auth methods, access model, API type/breadth, MCP availability, buildability) to compute match/mismatch counts and a field-accuracy percentage, and separately tally distributions and blocker categories across whatever's been researched so far. Free-text fields are deliberately excluded from the accuracy count, since independent model runs word them differently by nature.

n8n Code nodes JavaScript

Honest gap: this pipeline doesn't touch Composio's own SDK or MCP anywhere — it's Tavily for search and Claude for reasoning, orchestrated by n8n. A script built on Composio's SDK would dogfood the product being evaluated more directly; that's the next thing to change, not just the app count.

Verification — did the agent's answers hold up?

Salesforce and HubSpot, each re-researched independently, field by field on the six controlled-vocabulary fields.

75% of compared fields agreed across both apps (9 of 12) — but 0 of 2 apps agreed on every field

The disagreements aren't noise — they're the verification agent finding real things the first pass missed. For Salesforce, it surfaced Basic Auth and a Streaming API the original research didn't mention. For HubSpot, it surfaced a legacy API Key path. In both cases the independent pass added coverage rather than contradicting it — which is a better outcome than a clean match would have been, since it shows the second check is actually catching gaps, not just agreeing by default.

What's visible so far

One full category (CRM and Sales, 10/10) — real enough to state with some confidence for this category, still too narrow to generalize to the other nine.

9/10

Self-serve at some tier — free dev edition, instant API key, or OAuth app registration with no approval gate. The one exception, DealCloud, requires an existing paid customer site before API access is even possible — a genuinely different access model, not just a stricter version of the others.

8/10

Already have some form of MCP support (native, hosted, or community). The two without it — Copper and DealCloud — are also the two with the least open access model, suggesting MCP availability tracks with how open the platform already is, not the other way around.

10/10

OAuth2 shows up in every single app — it's the universal baseline for this category, not one option among several. API Key appears in 6/10 as an additional server-to-server path; a buildability check that only looks for "does it support OAuth" would miss nothing here, but that may not hold outside CRM.

All 10 apps are from category 1 (CRM and Sales) — the other 9 categories (support, comms, martech, ecommerce, data/SEO, dev infra, productivity, fintech, AI/media) are entirely unresearched. These are category-specific observations, not platform-wide patterns yet.
